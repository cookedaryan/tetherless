# Contributing

Every rule here exists because breaking it caused a real problem in this repository. Where that is
the case, the problem is named — a rule whose reason is visible is one people can apply judgement to
rather than route around.

---

## Getting set up

```bash
bash scripts/generate-dev-cert.sh
```

```bash
git config core.hooksPath scripts/git-hooks
```

Both are once per clone, and both matter. Without the certificate every test that opens a TLS socket
fails, and the failure looks nothing like a missing file. The hook refuses text files containing NUL
bytes or a UTF-16 byte-order mark, because several files here were silently corrupted by shell
redirection writing UTF-16LE — the result looks fine in an editor and breaks the build.

```bash
./gradlew build
```

Compilation, Checkstyle, SpotBugs with find-sec-bugs, and the unit suites. It has to be green before
you open a pull request.

```bash
./gradlew :chat-desktop:integTest
```

The end-to-end harness. Slower, because it boots a relay and opens real sockets. Run it for anything
touching the protocol, the transport, the session logic or the relay.

## Security rules

These are not negotiable, and a change that breaks one will be sent back regardless of what else it
does.

**Payload bytes, IVs, keys, shared secrets and passphrases are never passed to a logger, at any
level, including TRACE.** A log line lives longer and travels further than anyone writing it
expects — into a bug report, a support ticket, a screenshot. Use `Redact.id()` for peer ids.

**Nothing secret goes into a process argument list.** Identity keys were once generated by running
`keytool` with the user's passphrase as an argument, where any process running as the same user
could read it. Prefer stdin, a file, or doing the work in process.

**No Java serialization on the wire path.** No wire type implements `Serializable`, and `readObject`
appears nowhere that touches network input. Deserializing untrusted bytes is a remote-code-execution
class of bug that lives in whatever is on the classpath, not in the code you wrote.

**No trust-all `TrustManager` and no hostname-verifier override — not even behind a debug flag.**
A flag that disables certificate checking will eventually be set in something that ships. Configure
a truststore instead; see `TlsSupport`.

**Read a length before you allocate for it.** Every variable-length field on the wire is capped and
the cap is checked first. A reader that trusts a declared length hands the sender control of the
heap.

**Do not weaken a check to make a test pass.** If a test fails against a security control, either
the control is wrong — in which case say so and change it deliberately — or the test found
something.

**A check must run on the receiving side, not only the sending one.** Several defects here were a
value that one end wrote correctly and the other end never read back: a receiver id covered by a
signature and never compared, a nonce direction bit set on every send and ignored on every receive,
a sender id the relay forwarded without checking against the connection it arrived on. Writing a
field is not enforcing it.

**Fail closed.** A truststore that will not open, a peer key store that will not parse, a
registration that cannot prove itself: refuse. Continuing with less security than intended, having
logged a warning about it, is the failure mode this codebase treats as worst — it does not look
like an incident and it is the one an attacker would choose.

**Do not describe a guarantee you have not checked.** Three of the findings in the last audit were
comments and documents asserting the opposite of what the code did — a suppression file explaining
that it contained no blanket suppressions directly above two of them, a deployment guide promising
hostname verification that was switched off, a security document counting three scoped exclusions
where there were one. Prose is not enforced by anything. When you write that something holds, link
the test that makes it hold.

## Changing the wire format

The encoding is a compatibility surface. `MessageCodec` writes the enum **ordinal**, so the order of
`MessageType` constants is part of the format.

- Append new message types. Never reorder, never remove.
- Any change to the encoded bytes is a protocol break and must bump `protocolVersion`.
- `ProtocolVectors` freezes 17 wire-format cases. If your change makes `ProtocolVectorsTest` fail,
  that is the design working: the test is telling you the format moved. Update the vectors
  deliberately, in the same commit, with the version bump.
- The vectors run on the JVM and on a real Android runtime in CI, because Android's crypto comes
  from Conscrypt rather than the JDK and the two have disagreed before.

[docs/protocol.md](docs/protocol.md) describes the format as it stands. Update it in the same commit
as any change to it.

## Tests

**Write the test first, watch it fail, then make it pass.** A test that has never failed has not
been shown to test anything. This is not a style preference: three defects in the transport layer
were found precisely because the tests written for them failed the first time.

**Assert on what reached the user, not on what was logged.** A message that was dropped with a
warning and a message that was rendered are different outcomes, and only one of them is a security
property.

**Make a security test fail on purpose before you trust it.** Disable the control it covers and
confirm the test goes red. Several tests in this repository were validated that way, and it is
recorded where it was done.

This is not a formality. During the audit remediation, three tests written *for* the fixes passed
against the unfixed code and would have shipped as false assurance: one leaned on a signature policy
that exempts the frame type it was testing, one assumed `Properties.load` throws on a corrupt file
when it usually does not, and one asserted on a payload that does not carry the field being forged.
Each was caught only by reverting the fix and watching the test stay green. Where a defect is one a
mutation can simulate — a truncated counter, a dropped check — mutate it and confirm the failure;
`IvReuseTest` was validated that way and says so.

**Do not stub out the thing under test.** An earlier version of `ConnectionManagerTest` overrode the
connect method entirely and opened a server socket nothing ever connected to; it passed, and covered
nothing about connecting.

**Keep Swing out of unit tests.** Logic belongs in testable non-UI classes. The few tests that do
need a display skip themselves where there is not one, which is how CI runs.

## Style

Checkstyle and SpotBugs run on every build and failures break it. Beyond that:

- Match the file you are editing.
- Comments explain **why**, not what. The code says what it does; a comment earns its place by
  saying what would otherwise have to be rediscovered — a constraint, a failure that motivated the
  design, a trade-off someone would otherwise undo.
- Prefer a named constant with a comment over a bare number.
- `find-sec-bugs` runs at high confidence and fails the build. `./gradlew check -PspotbugsAll`
  lowers the threshold when you want to look below it. Suppressions go in
  `config/spotbugs/exclude.xml`, scoped to a single class or method and carrying their reason.
  Blanket pattern suppressions are refused: on a security detector they silently cover code nobody
  has looked at yet.

## Commits and pull requests

Write the commit message for someone who will read it in a year while trying to understand why the
code is the way it is. Say what changed and why; if you found something along the way, record it.

Before opening a pull request:

- `./gradlew build` is green.
- `./gradlew :chat-desktop:integTest` is green, if you touched anything it covers.
- Documentation affected by the change is updated in the same commit —
  [protocol.md](docs/protocol.md) for the format, [security.md](docs/security.md) for anything that
  changes what is or is not protected, [adr.md](docs/adr.md) for a decision that would be expensive
  to reverse.
- Anything you found but did not fix is written down somewhere a person will see it, rather than
  left for the next reader to rediscover.

## Reporting a vulnerability

Privately, and not as a public issue. See the reporting section of
[docs/security.md](docs/security.md). A report that comes with a failing test against
`MaliciousRelay` is especially welcome.
